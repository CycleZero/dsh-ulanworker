# handoff

把这段会话压成一份**能被陌生人接手**的文档。接手方看不到这段对话，只有你写下的东西 —— 所以按"对方对这个项目一无所知"来写。

最终产物是一段**自包含**的纯文本，会被当作**新会话里用户说的第一句话**粘贴进去。

# PHASE 0 — 先确认这次交接值得做

- [ ] 本会话确实有值得保留的实质工作或上下文
- [ ] 用户是真的要一份交接文档，而不是在问怎么做交接

如果会话几乎是空的、或没有实质上下文，**直接告诉用户没有值得交接的东西**，不要产出空文档。

# PHASE 0.5 — 先读会话，逐字取回原始诉求（强制的第一步数据操作）

**不要凭记忆重建用户的原始诉求。** 长会话和压缩后的会话会截断或摘要早期消息，上下文里的记忆不可靠。

DSH 把每个会话以 zstd 压缩的 JSONL 持久化在磁盘上，可以逐字读回：

```bash
python3 - "$PWD" <<'PY'
import json,os,sys,subprocess,glob
p=sys.argv[1]
slug='--'+''.join(c if ord(c)<128 else '~%04x'%ord(c) for c in p.strip('/').replace('/','-'))+'--'
dirs=glob.glob(os.path.expanduser('~/.dsh/sessions/'+slug+'/*/'))
if not dirs: sys.exit('没有找到本工作区的会话目录：'+slug)
f=max(dirs,key=lambda d:os.path.getmtime(d))+'session.v4.jsonl.zstd'
out=subprocess.run(['zstd','-dc',f],capture_output=True,text=True).stdout
for line in out.splitlines():
    if not line.strip(): continue
    o=json.loads(line)
    if o.get('type')=='user/message' and o.get('data',{}).get('source',{}).get('kind')=='user':
        print(''.join(pt.get('text','') for pt in o['data']['content'] if isinstance(pt,dict)))
PY
```

这会按时间顺序打印本会话里**用户真正输入过**的每一条消息。

**必须按 `source.kind == 'user'` 过滤。** 同一份日志里的 `user/message` 事件有三种来源：

| `source.kind` | 是什么 |
|---|---|
| `user` | 用户真打进去的字 ← **只要这个** |
| `runtime-context` | 运行时上下文注入块 |
| `skill-catalog` | skill 目录注入块 |

只按"第一条 role 为 user 的消息"来取，会取到注入内容而不是用户的诉求。这是 DSH 与 OpenCode 的关键差异，别照搬 OpenCode 的做法。

拿到输出之后：

1. 第一条就是用户的原始诉求，**逐字**抄进工作笔记，稍后原样放进 `USER REQUESTS (AS-IS)`。
2. 用户如果发过多条彼此独立的顶层请求（不是追问补充），也逐字收齐每一条。
3. 规则：
   - 不从记忆重建用户请求，一律从日志输出里引用
   - 不转述、不摘要、不"顺一下"用户的措辞
   - 即便你觉得你记得第一条消息，也不要跳过这一步
   - **读不到就明说读不到**（在 `USER REQUESTS (AS-IS)` 里说明），绝不猜

# PHASE 1 — 程序化取证

按顺序执行，收集具体数据：

1. 上面那份会话日志（PHASE 0.5 已经跑过，**复用**，不要重跑）
2. 你当前的 todo 列表 —— 它就是 live 的计划状态
3. `git diff --stat HEAD~10..HEAD` —— 最近改动了哪些文件
4. `git status --porcelain` —— 未提交的改动

如果当前目录不是 git 仓库，跳过 3 和 4，并在 `CURRENT STATE` 里说明"非 git 仓库"。

从这些输出里判断：做完了什么、还剩什么没做完（含 todo 状态）、做过哪些决策、哪些文件被改过或讨论过、确立过哪些模式/约束/偏好。

`USER REQUESTS` 已经在 PHASE 0.5 从日志逐字取好了，这里不要重新推导。

# PHASE 2 — 提炼

用**第一人称**写（"我做了…"、"我告诉过你…"）—— 因为这段文字会被当作新会话里**用户自己说的话**粘贴进去。

聚焦：

- 讲**能力和行为**，不讲逐文件的实现细节
- 只留对"继续这项工作是必须的"东西
- 除非关键，否则不写变量名、存储键、常量
- `USER REQUESTS` 和 `EXPLICIT CONSTRAINTS` 只能逐字，不许发明

提炼时自问：我刚做了什么？我给过哪些**仍然相关**的指示（比如"照着代码库现有模式写"）？我说过哪些文件重要、我正在动哪些？我给过计划或规格吗？我交代过哪些库、模式、约束、偏好？我发现了哪些关键技术细节（API、方法、模式）？我发现过哪些坑、限制、未决问题？

# PHASE 3 — 固定格式（九节，一字不改）

严格用下面这个格式和这些节标题：

```
HANDOFF CONTEXT
===============

USER REQUESTS (AS-IS)
---------------------
- [逐字用户原话 —— 不许转述]

GOAL
----
[一句话，说明接下来要做什么]

WORK COMPLETED
--------------
- [第一人称，做完了什么]
- [相关处给出具体文件路径]
- [关键实现决策]

CURRENT STATE
-------------
- [代码库或任务的当前状态]
- [构建/测试状态（如果适用）]
- [环境或配置状态]

PENDING TASKS
-------------
- [计划了但没做完的]
- [接下来合乎逻辑的步骤]
- [遇到的阻塞或问题]
- [当前 todo 状态]

KEY FILES
---------
- [路径] - [一句话作用]
（最多 10 个，按重要性排序）

IMPORTANT DECISIONS
-------------------
- [做过的技术决策以及为什么]
- [考虑过的取舍]
- [确立的模式或约定]

EXPLICIT CONSTRAINTS
--------------------
- [只放逐字约束 —— 来自用户或 AGENTS.md]
- 没有就写：None

CONTEXT FOR CONTINUATION
------------------------
- [接手的会话需要知道什么才能继续]
- [要当心的警告或坑]
- [相关文档引用]
- DEAD ENDS: [试过但走不通的路 + 失败原因 —— 有就必写，这条最省接手方时间]
```

**格式硬规则：**

- 纯文本加项目符号
- **内容里不许出现 `#` 标题** —— 用上面那种 `---` 下划线式
- **内容里不许有粗体、斜体、代码围栏**
- 文件路径用**工作区相对路径**
- 保持聚焦，只写对继续有用的；但"对继续有用的"要写全
- 长度按任务复杂度定

# 落盘

除了打印，也写到 `<workspace>/.dsh/handoff/<YYYYMMDD-HHmmss>-<slug>.md`（`<slug>` 是 2–4 个英文短词）。文件开头加元信息：

```
> 生成时间：<ISO 8601>
> 工作目录：<绝对路径>
> 相关文件：<主要涉及的文件，逗号分隔>
> 会话：<session id；不确定写「未知」，不要编>
> 来源：/handoff
```

落盘只是备份 —— 粘贴用的那段必须是**自包含**的，不能依赖对方去打开这个文件。

# PHASE 4 — 给用户继续用的说明

生成完之后，把下面这段附在回复末尾：

```
---

在新会话里继续：

1. 开一个新会话（或者恢复本会话）
2. 把上面的 HANDOFF CONTEXT 整段作为第一条消息粘进去（也可以 @ 引用落盘的那个文件）
3. 补上你的需求："从上面的 handoff context 继续。<你的下一步>"
```

# 硬性约束

- **绝不**尝试用程序方式创建新会话
- **必须**自包含：脱离本会话、脱离那个文件也能用
- **必须**用工作区相对路径
- **绝不**包含敏感信息 —— API key、凭据、密钥、token、内网地址。粘贴前扫一遍
- `KEY FILES` **不超过 10 个**
- `GOAL` **一句话**或一小段
- `USER REQUESTS (AS-IS)` 与 `EXPLICIT CONSTRAINTS` **只能逐字**
- **不许编造。** 不确定的写「未知」「未验证」。一个编造的细节比一个缺失的细节糟得多
- **不写指代。** 不写"上面那个文件""刚才那个 bug"，写全路径、全名、全命令

# 与相邻机制的分工

| 机制 | 用途 |
|---|---|
| `/compact` | 压**当前**会话继续用，产物留在上下文里 |
| `/handoff` | 产出**可带走**的文档，给别的会话、别的人、别的工具 |
| `create_goal` | 同一个会话跨轮持续，不换会话 |
| ultrawork 的交接块 | **会话内**汇报用的五要素块（ASK/WANTED/KNOW/NOW/NEXT），不跨会话 |

上下文快满时：先 `/handoff` 落盘，再开新会话。不要硬撑到自动压缩把细节丢掉。

- [ ] `GOAL` 是一句话？
- [ ] `KEY FILES` 不超过 10 个？

- [ ] 扫过一遍敏感信息，没有 key / token / 凭据？
